## 1. 왜 `strategy-builder`로 충분하지 않은가

`strategy-builder`는 **사용자와 대화하며** 전략을 만드는 에이전트다. 사용자의 역할:

- 의도 입력 ("RSI 30 이하에서 매수, 15% 수익 시 익절")
- 파라미터 선택
- 생성 결과 확인 후 활성화 클릭

이 구조는 두 가지 전제를 강제한다:

1. **사용자가 대화 루프의 필수 참여자다.** 없으면 파이프라인이 멈춘다.
2. **사용자의 판단이 품질 게이트다.** 나쁜 스킬을 거르는 것은 사용자의 "거부" 클릭이다.

사용자가 명시한 시스템 목표와 정면 충돌:

> "백엔드에 집중되어 있는 코드를 스킬 형태로 이전한 이유는 AI 중심의 시스템을 만들기 위해서야. 즉 담당 에이전트가 기존 스킬을 분석해서 새로운 스킬을 자동으로 만들 수 있어야 해."
>
> "사용자가 전략 스킬을 만드는 것이 아니라 에이전트가 스스로 만들 수 있어야 해."

→ 대화 루프에 사용자가 없어야 한다. 품질 게이트는 기계적이어야 한다.

이것이 `skill-architect`라는 별개 에이전트를 만드는 이유다. `strategy-builder`를 재설계하지 않는 이유는, 사용자 대화형 도구는 여전히 가치 있고 (사용자가 명시적으로 새 전략을 주문하는 경우) 자율 경로와 섞이면 안전 경계가 흐려지기 때문이다.

## 2. 자율 생성의 5가지 필수 조건

사람이 없는 루프에서 스킬을 만들려면 5가지가 모두 갖춰져야 한다.

### 2.1 Trigger (무엇이 스킬 생성을 시작시키는가)

**대답**: 구조화된 gap signal.

`meta-learner`, `self-critic`, `tech-scout` 세 에이전트는 이미 "현재 시스템이 무엇을 못하는지" 식별하는 역할을 맡는다. 이들의 출력이 JSON 신호가 된다:

```json
{
  "source": "meta-learner",
  "signal_id": "GAP-20260408-001",
  "gap_type": "missing_capability",
  "summary": "변동성 레짐 판별 기능 부재로 추세장/횡보장 구분 없이 마틴게일 적용",
  "evidence": {
    "observations": ["..."],
    "sessions": ["M003", "M009"],
    "sample_size": 23
  },
  "proposed_intent": "1분봉 200개로 레짐 점수 산출",
  "kpi_target": {"metric": "monthly_return_compound", "threshold": 12.0, "comparator": "ge"},
  "confidence": 0.72
}
```

품질은 `sample_size`와 `confidence`로 가드된다 (D-007: `sample_size < 10` 또는 `confidence < 0.5`는 즉시 `insufficient_evidence`로 거부).

### 2.2 Intent Specification (사용자 없이 "무엇을 만들지" 결정)

**대답**: Gap signal을 입력으로 받는 self-specification 루프.

사용자가 없으므로 "어떤 입력을 받을지", "어떤 출력을 낼지", "어떤 가정을 할지"를 스스로 명시해야 한다. 핵심은 **모든 가정에 `confidence` 필드를 달아 검증 루프에서 반증할 수 있도록** 하는 것.

```json
"assumptions": [
  {"text": "1m 봉 200개로 충분한 신호 추출", "confidence": 0.7},
  {"text": "ATR 기반 정규화로 코인 간 비교 가능", "confidence": 0.6}
]
```

`self-critic`이 "가정 2는 증거 부족"이라고 반박하면 revise/reject 루프로 돌아간다.

### 2.3 Code Generation (실제 파일 쓰기)

**대답**: Phase 3 thin wrapper 패턴 강제.

이게 Phase 3 consolidation 작업의 진짜 이유다. 순수 함수가 `backend/app/core/*.py`에 모여 있으면 (`waterfall_engine`, `symbol_score`, `binance_market_snapshot`, `position_math`), 스킬은 이들을 조합하는 얇은 래퍼가 된다:

- AI가 생성해야 할 코드 = 수십 줄의 glue code
- 품질 위험이 있는 신규 로직 = 최소화
- 검증 가능한 스킬 = 최대화

Gap이 "이 순수 함수가 없다"는 것이라면, skill-architect는 직접 코드를 쓰지 않고 `backend_change_proposals`로 에스컬레이션하고 멈춘다. 백엔드 변경은 일반 cio 리뷰 루프를 탄다.

Generated files는 반드시 `# AUTO-GENERATED by skill-architect` 헤더를 달아 사람이 수동 편집하지 못하게 표시한다. 수정이 필요하면 gap signal을 다시 내고 skill-architect를 재실행하는 것이 원칙.

### 2.4 Ground-Truth-Free Validation (사용자 판단 없이 품질 확인)

**대답**: 4단계 자동 검증 체인.

1. **Smoke run**: 고정 fixture로 `py_compile` + import + 기본 실행
2. **Paper backtest**: gap signal의 심볼/기간으로 `at-backtest/scripts/backtest.py` 실행
3. **KPI gate**: `monthly_return_compound`를 `strategy-evolver` 규칙으로 계산, threshold와 비교
4. **Reproducibility**: smoke run 재실행, 바이트 동일 출력 확인

KPI gate가 12% 복리에 미달하면 `verdict: "promising"` 까지만 허용, `"recommended"` 절대 안 됨. v1.5.12.0에서 이미 시스템 전반에 박힌 정책.

추가 게이트: `self-critic` 에이전트 의무 호출. "다른 AI가 이 AI의 작업을 리뷰"하는 ensemble 방어선.

### 2.5 Activation Gate (누가 enable 클릭을 대신 누르는가)

**대답**: `risk-manager` VETO + `cio` 승인 + `decision_log` 기록.

- `risk-manager`가 `vote: "VETO"`를 내면 스킬 파일은 디스크에 남지만 SKILL.md frontmatter에 `disabled: true`가 추가되고 `claude_meta_loader`가 `/api/v1/skills` 응답에서 제외
- 그렇지 않으면 paper mode로 활성화 (`ready_for_paper: true`)
- Live mode 승급은 여전히 **사용자 명시적 승인 필요** (`ready_for_live: false`). 의도적 제한 — 실제 자금 투입은 관제탑의 사람 감독자가 버튼을 누르는 마지막 경계

모든 결정은 `decision_log.md`에 `CIO-YYYYMMDD-NNN` 엔트리로 기록. 사용자의 유일한 감독 창구.

## 3. 현재 인프라 gap 분석

### 3.1 이미 있는 것 (재사용 가능)

| 인프라 | 상태 | 활용 |
|---|---|---|
| `/api/v1/skills`, `/api/v1/agents` | ✅ Phase 0 | Reuse Before Create 인벤토리 |
| `backend/app/core/*.py` pure functions | ✅ Phase 3 완료 | 스킬의 building blocks |
| `at-backtest/scripts/backtest.py` | ✅ 존재 | Paper validation |
| `at-strategy/references/decision_log.md` | ✅ 존재 | Activation audit trail |
| `risk-manager` 에이전트 | ✅ 존재 | VETO gate |
| `self-critic` 에이전트 | ✅ 존재 | Ensemble review |
| `meta-learner`, `tech-scout` | ✅ 존재 | Gap signal source |

### 3.2 필요하지만 없는 것

#### A. Function-Level Introspection API [P0]
**문제**: `/api/v1/agents`는 파일 단위 메타데이터만 제공. skill-architect는 "어떤 백엔드 pure function이 존재하는가"를 query해야 함.

**제안**:
- 신규: `GET /api/v1/backend-core/functions` — `backend/app/core/*.py`의 public 함수 목록 (이름, 시그니처, docstring 첫 줄)
- `claude_meta_loader`에 `list_core_functions()` 추가 — `ast.parse`로 함수 추출, TTL 60s 캐시

**위험**: 낮음 (읽기 전용).

#### B. Gap Signal 수집 엔드포인트 [P1]
**문제**: 현재 `meta-learner` 등의 출력이 구조화된 채로 저장되지 않음 (decision_log 텍스트에 섞여 있음).

**제안**:
- DB 테이블 `gap_signals (signal_id, source, gap_type, payload_json, status, created_at, processed_at)`
- API: `POST /api/v1/gap-signals`, `GET /api/v1/gap-signals?status=pending`
- skill-architect trigger는 이 큐에서 pull

**위험**: 중간 (DB 마이그레이션).

#### C. skill-architect 호출 스케줄러 [P1]
**문제**: gap signal이 생겨도 누가 skill-architect를 깨우는가?

**제안**:
- `cio` 에이전트의 INTELLIGENCE phase에 "pending gap_signals 확인 → skill-architect 호출" 단계 추가
- 또는 별도 cron (`at-orchestrator/scripts/gap_processor.py`)로 배치 처리

**위험**: 낮음 (기존 orchestrator 패턴 확장).

#### D. disabled Frontmatter 필터링 [P0]
**문제**: 현재 `claude_meta_loader.list_skills()`가 `disabled: true`를 필터링하지 않음.

**제안**:
- `list_skills()` 수정: frontmatter에 `disabled: true`가 있으면 제외
- skill-architect가 VETO된 스킬의 frontmatter를 수정할 수 있도록 Write 허용

**위험**: 낮음.

#### E. Skill Smoke Test 인터페이스 표준 [P0]
**문제**: 생성된 스킬이 "smoke run"에 응할 수 있어야 함. 지금은 스킬마다 CLI 인터페이스가 제각각.

**제안**:
- 새 스킬은 반드시 `python3 <script>.py --self-test` 플래그를 구현, 고정 입력에 대해 고정 JSON 출력
- skill-architect가 생성 시 이 handler를 boilerplate로 포함

**위험**: 없음 (관례만 수립).

### 3.3 작업 우선순위

```
[P0 - skill-architect 실행 전 필수]
  A. Function-level introspection API
  D. disabled frontmatter 필터링
  E. Smoke test convention 문서화

[P1 - 자동화 루프 완성]
  B. Gap signal 수집 DB/API
  C. cio 스케줄러 통합

[P2 - 품질 개선]
  - 추가 ensemble 검증자 (예: backtest-analyst 의무 호출)
  - Live mode 승급 정책 문서화
```

## 4. 운영 경계 (Hard Rules)

skill-architect가 절대 할 수 없는 것:

1. **Live (실거래) 세션 수정 금지** — `is_paper=True` 세션만 터치
2. **기존 live 스킬 파일 수정 금지** — 오직 생성만
3. **risk-manager VETO 우회 금지**
4. **decision_log 엔트리 생략 금지** — 감사 추적이 사용자의 유일한 창구
5. **12% KPI gate 미달 스킬을 recommended로 마킹 금지** — v1.5.12.0 정책
6. **사용자에게 질문하기 금지** — 대화 루프에 사용자 없음
7. **백그라운드 프로세스 스폰 금지** — 호출 범위 내에서만 실행

이 7가지는 `feedback_backwards_compatible_defaults` 원칙의 구체화 — "운영 세션을 깨는 default 변경 절대 금지".

## 5. 단계별 배포 계획

### Phase A: Foundation (인프라 P0)
- A, D, E 작업 완료
- skill-architect는 존재하지만 수동 호출만 가능 (사용자가 gap_signal JSON을 직접 prompt에 넘김)
- 1-2개 샘플 gap_signal로 시험 가동, 결과 검토

### Phase B: Semi-Autonomous (P1)
- B, C 작업 완료
- gap_signals 큐에 자동 누적, cio가 주기적으로 소비
- 생성된 스킬은 **paper 모드만** 활성, live 승급은 여전히 사용자 수동

### Phase C: Full Autonomous
- 충분한 샘플 축적 후 (`sample_size >= 30`)
- cio가 paper 모드에서 14일 이상 12% 복리를 유지하는 AI 생성 스킬을 자동으로 live 후보로 마킹 (승격은 여전히 사용자)
- 최소 2026-05 이후 고려

## 6. 이론적 가능성에 대한 직접 답변

**Q**: "이론적으로 가능한 작업이지?"

**A**: 그렇다. 그리고 Phase 3 consolidation 작업이 이를 구체적으로 가능하게 만들었다.

이유:
1. **순수 함수 라이브러리**가 backend/app/core에 모여 있다 — AI가 조합할 building blocks
2. **Thin wrapper 패턴**이 증명되었다 — martingale_base_runner.py 같은 기존 스킬이 reference
3. **기계적 품질 게이트**가 이미 운영 중이다 — 12% 복리, risk-manager VETO, self-critic
4. **감사 추적**이 이미 운영 중이다 — decision_log.md
5. **Ensemble 에이전트**가 이미 존재한다 — meta-learner (gap 탐지), self-critic (리뷰), risk-manager (게이트)

없는 것은 "gap signal 구조화된 큐"와 "cio 스케줄러 hook" 두 가지 배관 작업뿐. **3-5일의 엔지니어링 작업**.

### 정직한 경고

- **AI가 만든 스킬이 AI가 만든 스킬을 참조하는 재귀 깊이**가 발생하면 감시가 어렵다. Phase A/B 동안은 신규 스킬이 다른 자동 생성 스킬을 import하는 것을 금지하고, 오직 사람이 리뷰한 `backend/app/core/*.py` pure function만 import하도록 강제할 것
- **Gap signal의 품질이 skill-architect 품질의 상한**이다. meta-learner가 틀린 gap을 신호하면 아무리 완벽한 skill-architect도 무의미한 스킬을 생성한다. meta-learner의 감독이 먼저 강화되어야 한다
